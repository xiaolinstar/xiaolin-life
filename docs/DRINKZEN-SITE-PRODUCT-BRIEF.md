# DrinkZen Site 产品定位与首版方案

日期：2026-10-18。状态：供讨论与原型验证的产品方案，尚未实施。

## 1. 定位

DrinkZen Site 是 DrinkZen 的公开产品站：帮助用户认识产品、查询饮品、理解规格与营养差异，并进入小程序持续记录和管理饮用。网站的主线是用户的饮品决策，内容用于支持这些决策。

一句话定位：**查清一杯，选择一杯，记录每一杯。** 这是拟议的产品表达，需结合实际能力确认后再用于上线文案。

| 产品载体 | 主要职责 |
| --- | --- |
| DrinkZen Site | 产品介绍、公开饮品查询、规格与营养解释、使用帮助、小程序入口 |
| DrinkZen 小程序 | 饮用记录、个人预算、历史与日常使用；具体能力以当前产品为准 |
| DrinkZen Admin/API | 菜单、规格、营养、评级与来源的统一维护 |
| xiaolin-life | 保留原有网站与饮品文章，继续按作者意愿独立运营 |
| 社媒 | 小红书与大众点评共用一份内容，用于发现饮品、了解产品与回访 |

用户可以从搜索、社媒、博客链接或直接访问进入网站。公开查饮品无需先登录；涉及个人记录与预算时，再引导进入小程序。

## 2. 产品目标与边界

首版目标是让首次访问者能回答：DrinkZen 有什么用，这杯饮品是什么配置，营养资料是否足够可信，下一步如何使用小程序。

- 网站突出查饮品与理解规格，首页给清晰的产品价值和使用入口。
- 饮品默认按新加坡 Nutri-Grade 展示，上海标准可明确选择；评级标识始终带标准名称。
- 热量、糖、饱和脂肪和咖啡因分别表达；整杯与每 100ml 有明确口径。未知值保持未知。
- 官方、第三方检测、配方估算及资料缺失状态清楚可见。评级不提供人群适宜性或安全保证。
- 内部选题可关注职场日常的咖啡与饮用决策，公开文案不限定用户群体，不提供孕妇建议。
- 文章发布时间、作者动态和 plog 编辑流程不占据主导航；产品页按信息模块组织，资料较长时允许展开阅读。
- 首版沿用现有 Nuxt SSR 和公共 API，不恢复暂停维护的 H5，不复制小程序的完整个人数据功能。

## 3. 三条核心使用路径

### 路径 A：带着饮品名来查询

搜索品牌或饮品 → 打开产品详情 → 确认杯型、温度、糖度等真实选项 → 查看对应营养与评级 → 查看小程序入口或继续查另一杯。

成功标准：用户看到的是当前选中规格的数据，缺失项明确，不把默认杯的数据套给所有组合。

### 路径 B：还没决定喝什么

饮品库 → 选择品牌、单杯热量上限及明确标准的评级 → 查看候选饮品 → 打开详情确认规格。

首版的“热量上限”是用户临时输入的单杯筛选条件，不冒充其账号中的剩余每日预算。跨产品对比可在下一版加入，先保证筛选和单品规格可靠。

### 路径 C：首次认识 DrinkZen

首页了解“查询、选择、记录”的用途 → 查看一个真实饮品案例 → 了解来源与评级 → 进入小程序 → 阅读使用帮助。

成功标准：无需阅读一篇长博客，也能明白产品价值和下一步动作。入口点击与小程序实际访问/记录分别统计。

## 4. 信息架构

以下是建议结构；新增路由及功能均待开发与验证。

| 页面 | 建议地址 | 主要任务 |
| --- | --- | --- |
| 首页 | `/` | 产品价值、搜索、查饮品入口、小程序入口 |
| 饮品库 | `/products` | 搜索、品牌/热量/评级筛选，清楚呈现在售与历史状态 |
| 产品详情 | `/products/<id>` | 菜单选项、规格营养、评级解释、来源、使用入口 |
| 品牌目录与详情 | `/brands`、`/brands/<id>` | 找品牌与菜单；品牌介绍只保留与用户选择相关的内容 |
| 使用帮助 | `/help` | 如何查饮品、理解规格、在小程序记录与使用预算 |
| 数据与评级 | `/standards` | 来源口径、新加坡/上海标准、估算限制、纠错方式 |
| 饮品指南 | `/guides/<slug>` | 必要时解释点单问题与多产品差异；从相关产品可达 |

主导航建议为“饮品库 / 品牌 / 使用帮助”，小程序作为独立主按钮；首页通过 Logo 返回。“数据与评级”可放页脚并从评级旁进入。指南作为辅助知识，不以文章流作为首页主体。

保留现有产品与品牌 ID 路由，首版不叠加全站 slug 改造。最终路由需在原型验收时统一。

## 5. 关键页面内容

### 5.1 首页

1. 首屏：一句产品价值、饮品搜索框、“查饮品”和“打开小程序”的明确入口。
2. 功能说明：以真实页面或案例说明查询营养、根据单杯预算选择、在小程序记录；尚未上线的能力不作现成宣传。
3. 快捷查询：热门品牌或经核实的饮品入口；无实际行为数据时不将人工精选称为“用户最爱”。
4. 数据说明：简洁展示来源与默认评级规则，链接完整方法与限制。
5. 小程序介绍与入口：说明扫码/打开后能做什么；具体跳转能力先验证，保留适合设备的可用方式。

首页不直接复制博客摘要、作者信息、文章归档或社媒文案。首屏不使用“A 级放心喝”等保证性表达。

### 5.2 产品详情

建议从上到下排列：

| 模块 | 读者需要的信息 | 来源 |
| --- | --- | --- |
| 身份 | 品牌、官方菜单名、图片、在售/下架/未知、选中配置 | API 与菜单证据 |
| 规格选择 | 实际选项、默认值、互斥、加价；只开放真实可选组合 | API 菜单与规格 |
| 核心指标 | 每杯热量、糖、饱和脂肪、咖啡因；缺失状态 | 对应规格 API 数据 |
| 营养评级 | 标准名称、结果、判级依据、官方/计算/估算性质 | API 与统一规则 |
| 点单提示 | 已核实的选项差异、含醇或过敏原事实、数据限制 | 经过审核的内容模块 |
| 营养详情 | 每杯/每 100ml、配方假设及可追溯资料，长表可展开 | API 与注明版本的解释内容 |
| 体验补充 | 有真实作者记录时展示，并与营养事实分开 | 经作者确认的体验 |
| 来源与更新 | 来源、核对时间、估算限制、纠错渠道 | API/资料记录 |
| 下一步 | 继续查询、相关饮品、小程序入口 | 产品功能 |

菜单有某个选项，不代表该组合已有营养值。无法映射到实际规格时明确提示数据未完善，不能沿用另一规格的数值。下架历史页可继续查询，不能提示当前可购买。

### 5.3 数据与评级

以“怎么看懂数据”为主，解释：整杯与每 100ml、新加坡默认与上海可选、未知与零、官方与估算、来源与最近核对时间。信息贴近用户疑问，内部计算/审核操作保留在运营资料中。

## 6. 原博客内容如何复用

| 博客资料 | 目标站的处理 |
| --- | --- |
| 产品速览、菜单选项 | 与 API 核对后进入产品身份和规格模块 |
| 营养表、评级 | 复核后作为录入依据；页面统一使用 API 结果，原推算保留来源与假设 |
| 点单建议 | 变为关联选项/规格的简洁提示 |
| 真实口感、图片 | 变为可选体验模块与素材，注明作者及来源 |
| 科普与比较 | 形成帮助、标准说明或专题指南 |
| 品牌历史 | 选取与产品认知相关的信息，不复制大段行业介绍 |
| plog、标题公式、运营排期 | 作为内部运营资料，公开产品页不展示 |

所有饮品相关源资料可完整复制到内部来源档案，公开呈现按上述模块加工。一个原文可拆成多个模块，多篇原文也可合并支持一个产品任务；不要求源文件与公开页面一一对应。

两个网站可分别保留作者表达与产品表达。博客文章继续存在，目标站记录来源关系；不自动改写原文、重定向旧地址或替作者调整原站 canonical。

## 7. 视觉与文案方向

- 延续 DrinkZen 现有品牌标识和颜色，优先复用产品卡片、规格选择、评级标识等已形成的视觉语言。
- 信息层级以饮品名、当前配置、营养指标、明确下一步为主，减少大段介绍文字与装饰。
- 评级颜色配标准名称和文字，不只靠颜色传达；未知状态与低评级分开。
- 移动端优先，较多选项和营养表可滚动/展开，重要数值不被截断。
- 公开页面使用“查看营养”“选择规格”“在小程序记录”等具体动作；避免空泛的健康承诺。

## 8. MVP 与后续能力

| 优先级 | 能力 | 上线条件 |
| --- | --- | --- |
| 首版 | 产品价值首页、查询、品牌与详情、真实选项/规格营养、来源与评级、帮助、小程序入口 | 三类用户路径可用，指标对应规格，缺失状态正确 |
| 首版内部 | 内容来源档案、产品关联、共用 plog、发布记录、版本变化跟进 | 不泄露内部资料，发布事实可追溯 |
| 后续 | 2–3 杯对比、更多专题、来源变更提醒 | 有足够同口径资料，先验证实际需求 |
| 后续 | 更深的小程序来源归因、运营界面 | 有实际接入能力和重复劳动证据 |

首版无需建设完整 CMS、社交社区、Web 个人预算系统或自动发布社媒。所列后续能力不作为本次已授权实施范围。

## 9. 首个里程碑与评估

先完成首页、饮品库与一个产品详情的可交互原型，使用真实样本。验证用户能否完成：找一杯、看清配置、理解指标与来源、找到小程序入口，再确定视觉和功能方案。

随后使用 Manner 冰拿铁、瑞幸咸芝士豆乳拿铁、瑞幸埃塞金烘拿铁作为候选测试资料，覆盖公开文章、原草稿、多产品比较等情况；它们的源文件状态不决定目标站是否公开。

评估查询成功率、无结果/错误情况、规格数据完整性、产品页到小程序入口的点击及用户反馈。小程序真实访问和记录行为需要对应埋点，不由点击数推算；无基线时先建立观测，不预设增长数字。

先确认产品原型，再批量加工内容。完整实施顺序见 [内容复制与站点建设计划](DRINKZEN-SITE-MIGRATION-PLAN.md)。
